# 软件工厂共用尺子

四个角色的判定标准都来自这里。角色 skill 与本文件冲突时，以角色 skill 为准；本文件与用户当次指令冲突时，以用户指令为准。

## 问题分级

| 级别 | 定义 | 例子 | 对结论的影响 |
|---|---|---|---|
| Blocker | 会让默认分支不可用、或造成安全/数据损失 | 密钥硬编码、目录穿越、破坏既有接口契约 | 直接 fail |
| Critical | 验收标准未覆盖、契约偏离 | 某条 AC 无实现、返回字段与 design 不符 | 直接 fail |
| Major | 不影响正确性但影响可维护性 | 重复逻辑、命名误导、缺注释的关键分支 | 列入报告，不 fail |
| Minor | 风格偏好 | 空行、括号位置 | 只列，不 fail |

不确定该归哪级时，往低一级放，并在报告里注明"可升级"。

## 门禁阈值

- 硬门禁（零容忍）：设计符合性 100%、Blocker + Critical = 0、需求到代码覆盖 100%
- 软门禁（可留遗留项）：行覆盖 ≥80%、分支覆盖 ≥70%

不达标时最多回退修正 3 轮；第 3 轮仍不达标，停下来把现状写清楚交人工决定，**不要自行放行**。

## 三态判定

- pass：有证据，且证据直接支持该结论
- fail：有反证
- unknown：缺输入、缺命令输出、缺运行环境

`unknown` 既不算通过也不算失败。禁止使用"基本通过""看起来没问题""建议优化"这类无法判定的表述。

## 交接格式（四段，缺一段视为未完成）

1. **改了什么** — 对应 T-x 或 AC 编号
2. **依据** — 读了哪些上游产物、哪些代码文件
3. **怎么验证的** — 命令原文 + 退出码 + 关键输出行
4. **还剩什么** — 未完成项、待确认项

## 证据规范

- 结论必须能指到 `文件:行号`，或指到命令的原始输出
- 你自己的复述不算证据；"我运行了测试"不算，要有输出
- 没找到输入时，明确说缺什么，不要用常识补齐

## 本环境的三条硬事实（写命令时必须遵守）

- 每条 bash 调用都是**独立进程**，工作目录每次重置到线程工作区根。跨目录操作必须写成 `cd <目录> && <命令>`，上一条的 cd 不会带到下一条。
- 路径只能用相对路径或 `/mnt/user-data/...`、`/mnt/skills/...`；宿主绝对路径（`/d/...`、`~`、`$HOME`）会被拒绝执行。
- GitHub 通道**只出不进**：你的最终回答不会发到 Issue/PR，要说话必须在 run 内调用 `gh`。
